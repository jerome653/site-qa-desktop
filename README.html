SGEN Site QA

Install & update

How to get the app, and how it keeps itself current.

Engine 4.0.1Feed: jerome653/migration-qaSource: jerome653/site-qa-desktop

Install

  1. Run SGEN Site QA Setup.exe.
  2. Launch SGEN Site QA. It starts a local server and opens the window — nothing else is needed.

Everything runs on your machine. Scans, screenshots and reports never leave it. The only outbound request the app makes is checking the release feed for a newer engine.

How updating actually works

The app is split into two halves, and they update very differently. This is the single most important thing to understand.

PartWhat it isHow it updates
EngineThe QA code, rules and reports — the part that changes almost every release.Automatically. ~1 MB download, then relaunch.
ShellElectron + Chromium + the bundled browsers (~865 MB). Changes rarely.Manually — reinstall the .exe.

On launch the app polls version.txt on the release feed. If it is newer than what you have, the engine bundle downloads, its SHA-256 is verified against the published checksum, and it activates on the next relaunch. A failed checksum is never applied.

The repo must stay public

The app polls the release feed anonymously — it sends no credentials. If jerome653/migration-qa is made private, every install stops updating immediately (the poll 404s) and no engine ever lands again. The release assets are all the app reads; it never reads repo source. If the source must go private, move the three assets to a public feed repo and ship that new feed URL in a rebuilt installer first — existing installs have the old URL baked in and cannot be told about a new one.

Getting it from the repo

To run from source instead of the installer:

git clone https://github.com/jerome653/site-qa-desktop.git
cd site-qa-desktop
npm install
npm start

The bundled browsers/ folder (~685 MB) is not in git — the app needs it for rendering, so a source checkout must repopulate it (see DEV-HANDOFF.md §4).

To build a fresh installer:

npm run dist        # electron-builder --win nsis --x64
                    # output lands in release/

Publishing an engine update

This ships to every install. The order matters:

pwsh -File publish-engine.ps1 -Version 4.0.2
  • It stages from engine/ in this folder — not from git. Whatever sits there is what ships. Confirm the staging tree holds the code you mean to publish before running it.
  • Payload and checksum upload first; version.txt flips last, because that file is the trigger.
  • Do not fetch the canonical version.txt between staging and flipping — doing so has warmed the CDN edge with the old value and served a stale marker for ~10 minutes.
  • Verify by downloading the payload back and comparing SHA-256. The upload tool reports success even when it prints nothing.
  • Every shipped version needs an entry in CHANGELOG (in engine/sgen-qa-serve.js), or it appears in Logs → Versions as a bare timestamp with no explanation.

Reading a report

Red means passing. The report uses an inverted status palette; it prints its own legend saying so. Let the page settle for a second before reading numbers — the score ring and the dashboard tiles count up from zero, and a number read mid-animation is not the real number.

Two figures are reported and they measure different things: score is a raw pass ratio (it weights a missing alt attribute the same as a site-wide NOINDEX), while quality is a weighted risk model (0–100) — the more honest of the two.

Scores changed in 4.0.0

Three sets of checks — content artifacts, spelling, and the whole Best Practices section — were built and shipped but had never actually run. They run now, so most sites score slightly higher. Scans from 4.0.0 onward are not comparable to earlier ones. Re-baseline before comparing a site to its own history.
